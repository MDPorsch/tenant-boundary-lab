# Decisions

Accepted trade-offs and spec interpretations. "Owner approval" = the shared standard requires a human
to confirm it before the dependent milestone proceeds. Each entry says what was chosen and why, so
it can be challenged.

| ID | Decision | Owner approval |
|---|---|---|
| D-01 | **Python 3.13** via `uv` (3.13.18 installed with `uv python install`). `requires-python = ">=3.13,<3.14"`. The machine's system Python 3.14.7 is deliberately not used; 3.14 is added only after dependency compatibility is verified (spec). | No |
| D-02 | `src/` layout, package `tenantlab`, `uv_build` backend, `uv.lock` committed. Dependency ranges have upper bounds; exact versions live in the lockfile. `pyproject.toml` author has **no e-mail** (privacy). | No |
| D-03 | **Token verification:** PyJWT (with `cryptography`), algorithm **EdDSA/Ed25519 only**, pinned by the verifier; required `sub jti iss aud iat nbf exp`; leeway 0 s; max lifetime 900 s; verifier holds a **public** key only; other claims ignored. Tokens in tests are minted by the harness with ephemeral in-memory keys. | **Yes** (auth/token format) |
| D-04 | **Object ownership never grants rights.** `projects.owner_principal_id` is informational. Fixture trap: PA1's owner is Frank, whose membership is revoked (TL-03). | **Yes** (policy) |
| D-05 | **Resource scope (market) is evaluated before role.** The shared standard lists role/capability before scope, but then a hidden-market object would answer 403 to a viewer and 404 to a non-member, which discloses existence. Scope first makes "not visible" one 404 for every role. The capability gate still precedes body parsing and every side effect. | **Yes** (deviation from standard) |
| D-06 | **Concealment:** every "not visible" case is the same `404 resource.not_found`; "visible but not allowed" is `403 authz.forbidden`; a suspended tenant is disclosed (`403 tenant.suspended`) only to its active members. | **Yes** (policy) |
| D-07 | Fixture addition **gina**: owner of suspended tenant C. The spec lists tenants A/B/C but no member of C, which TL-14 needs. | **Yes** (spec addition) |
| D-08 | Added `GET /v1/tenants/{tenant_id}/me` (context probe). It gives every negative test a positive control (a deny-everything app would otherwise pass them) and proves roles come from the DB. Exposes only the caller's own `principal_id`, `tenant_id`, `role`. | **Yes** (spec addition) |
| D-09 | Added the nested route `GET /v1/projects/{project_id}/invoices/{invoice_id}`. TL-07 is defined on a nested route but the spec's API table has none. | **Yes** (spec addition) |
| D-10 | **Audit policy:** pre-authentication failures (401, 413) write **no database row** (spec TL-01/02 "no DB change"; prevents anonymous audit flooding), only structured logs. Later denials write one row; `tenant_id` is NULL unless the actor is an active member of the resolved tenant and the target is visible (nobody can write into another tenant's audit log, and hidden vs missing objects leave identical rows). Mutations and private-contact reads are audited; ordinary successful reads are not (write amplification). | **Yes** (policy) |
| D-11 | An authenticated caller sending a malformed UUID path identifier gets `422 request.invalid` after gates 1-2: it cannot name any resource, so there is nothing to conceal. | No |
| D-12 | Unknown JSON properties and unknown query parameters are **rejected** (422), not ignored. The spec says "ignore/reject" for an unauthorized `owner` field; rejecting makes mass-assignment attempts visible and testable. | No |
| D-13 | The private-contacts route answers **403** to editor/viewer; it never returns 200 with fields removed ("no BOPLA fallback"). | No |
| D-14 | Cursor pagination only (`limit` 1..100, default 25, `cursor` <= 256 chars); `page`/`offset` are unknown parameters. `total` counts only objects the actor may read. | No |
| D-15 | `Settings.database_url` is a **synchronous** SQLAlchemy URL and the app uses synchronous sessions (FastAPI runs them in a threadpool). Simplest correct basis for PostgreSQL row-locking tests in M5. The tests' DB snapshots use a sync engine. | No |
| D-16 | **Licence: Apache-2.0** (`LICENSE`, `NOTICE`; SPDX `Apache-2.0` in `pyproject.toml`). Chosen by the agent on 2026-11-19 under the owner's instruction "do what needs to be done"; the owner had not named one, so it was an assumption until the owner replied "License Confirmed" on 2026-11-20 (and gave the copyright holder's name, which `NOTICE` and `pyproject.toml` now carry; still no e-mail address). Why this one: an explicit patent grant and a NOTICE for the "deliberately vulnerable, no warranty" statement. The no-employer/client-code check was done by the agent against the history (clean). | **Given** (2026-11-20) |
| D-17 | **Red tests are real failing tests**, marked `milestone("Mx")`, never `skip`/`xfail`. `pytest` exits non-zero until M1 ships. `pytest -m "not milestone"` is the green contract suite. | No |
| D-18 | **Bodies are parsed after the gates** (found while validating tests against a spike: FastAPI parses JSON before dependencies, which would make anonymous malformed JSON a 422). | No |
| D-19 | Request ids are server-generated UUIDv4, returned as `X-Request-ID`, and equal the problem `request_id` and the audit `correlation_id`. A client value is never reused. | No |
| D-20 | **The repository is public** (owner instruction 2026-11-19: "make this repo public"). Made public on 2026-11-19 after CI had run green while it was still private (one real failure was found and fixed first: the container image build broke when licence files were added, commit 0bdec2b). Security settings: D-51. The repository contains a deliberately vulnerable lab; see SECURITY.md and `docs/vulnerable-lab.md`. | Given |
| D-21 | **Two independent policy copies.** The application has its own hand-written role/capability table (`auth/policy.py`); it does not load `capabilities.csv`. `test_app_policy_matches_oracle` compares the two cell by cell and `test_app_independence` forbids `api`, `auth` and `db` from importing the oracle (the mirror of the oracle guard). If both read one file, a bug in the loader or the data would be copied to both sides and every test would still pass. | No |
| D-22 | **Unknown routes are one generic 404.** An unknown path, a wrong method on a known path, a trailing slash and the docs/OpenAPI URLs all answer `404 resource.not_found`: no 405, no `Allow` header, no redirect, and no Swagger/ReDoc/OpenAPI routes at all (the contract is `docs/api-contract.md`; a test pins the exact route set). One concealment shape, nothing to probe, smaller unauthenticated surface. | No |
| D-23 | **Gate 0 details.** A declared `Content-Length` above 65 536 gets `413` before authentication, for everyone. A malformed or repeated `Content-Length` gets `422 request.invalid`, also before authentication and unaudited. A body with no declared length is counted as it is read (after the gates, D-18), so an unauthenticated chunked request gets `401` and its body is never read (L-15). | No |
| D-24 | **Audit `resource_id` of a denial** is the identifier the caller asked for, only after it parsed as a UUIDv4 (`NULL` when it was malformed). For collection routes it is the parent: the tenant for `/projects` and `/audit`, the project for `/contacts`, the target principal for `/members/{id}`; `resource_type` says which kind. Rows with `tenant_id` NULL are never returned by the audit endpoint, so recording a hidden id exposes nothing to a tenant. **Provisional for contacts and members until M2.** | **Yes** (policy), **approved 2026-11-19** |
| D-25 | **Invoice visibility is decided in the gate, before role.** An invoice is visible only if its own tenant equals its project's tenant (an incoherent row is a plain 404 with a NULL-tenant audit row, like any hidden object); the nested route additionally requires the invoice to belong to the project in the path. M2's TL-07 tests the handlers on top of this. | **Yes** (policy), **approved 2026-11-19** |
| D-26 | **The verifier is stricter than D-03's contract:** exactly one `Authorization` header; scheme `Bearer` matched case-insensitively (RFC 9110) with one space; token in compact form and at most 2048 characters; `aud` must be a single string (a one-element list is refused); `iat`/`nbf`/`exp` must be integers (no floats, no booleans); `jti` a non-empty string of at most 128 characters; `sub` a canonical lowercase UUIDv4. `kid`, `jku`, `x5u` and `jwk` headers are ignored and never fetched. | **Yes** (extends D-03), **approved 2026-11-19** |
| D-27 | **Database rules.** SQLite is for lab and tests only: `NullPool`, `PRAGMA foreign_keys=ON` on every connection, in-memory databases refused. `seed_fixtures` refuses a non-empty database and runs as one transaction. `audit_events` is append-only by convention, not by trigger (L-17). Project status is `draft\|active\|archived` (from `field_policy.csv`); invoice status is only length-bounded until M2 defines its values. Project/invoice tenant coherence is deliberately **not** a composite foreign key, because TL-07 must be able to inject an incoherent row to prove the service layer refuses it. | No |
| D-28 | **Fail closed on any database error.** A failed lookup, and also a failure to record the audit row of a denial, answers `503 service.unavailable` with a generic body. The class name is logged, never the statement or its parameters. A denial that cannot be audited is therefore reported as 503, not as the 403. | **Yes** (policy), **approved 2026-11-19** |
| D-29 | **Logging.** Pre-authentication rejections and denials emit structured records on `tenantlab.*` loggers (`event`, `request_id`, `reason`, `route`): never a token, body, e-mail or SQL. The package configures no handler; the operator chooses the sink (L-18). | No |
| D-30 | **Request body rules.** `Content-Type: application/json`; a non-empty UTF-8 object; duplicate keys, `NaN`/`Infinity`, lone surrogates and over-deep nesting are refused; types are strict (no bool-as-int, no string-as-number); `row_version` and `version` are 1..2147483647 so they fit every database; a `title` has 1..120 code points with no control (`Cc`), surrogate or bidi-override character. A 422 reports locations and codes only; unknown key names are never echoed. | No |
| D-31 | **Create in a market the tenant may not use is `403 authz.market_denied`, and a market that does not exist gets the same answer**, so the 403 cannot be used to map the market catalogue. Gate 7 runs before body validation whenever `market` is a string, as `gates.csv` orders it. | **Yes** (policy), **approved 2026-11-19** |
| D-32 | **Project quota is 1 000 per tenant and counts every project of the tenant, hidden-market ones included**, because the limit protects storage, not visibility. It is enforced inside the insert statement. Consequence: an editor who reaches the limit learns that at least 1 000 rows exist. | **Yes** (policy), **approved 2026-11-19** |
| D-33 | **Pagination** is keyset on `id` (ascending for projects and contacts, descending for audit). The cursor is the base64url of the last id and is **not signed**: it can only move the start point inside the caller's own readable set, so it reveals nothing about hidden ids. `total` is the readable count. | No |
| D-34 | **`PUT /members/{principal}` updates an existing membership only** (`field_policy.csv`: create is `n/a`); an unknown member is 404. It can re-activate a revoked member. `version` is a precondition (409 stale). Removing the last active owner, by demotion or revocation, is `409 conflict.last_owner`, decided inside the update statement. Gate 10 therefore also covers memberships (`gates.csv` updated). | **Yes** (policy), **approved 2026-11-19** |
| D-35 | **Mutations re-check authority atomically** (closing L-16 for single-statement SQLite writes; PostgreSQL row-lock behaviour is proven in M5): the `UPDATE`/`INSERT` carries the membership, role, tenant-state, market, quota and version predicates. A write that changes no row re-runs the gates to name the true reason. | No |
| D-36 | **Bounds.** A project detail embeds at most 100 contacts; private contacts and audit are paginated; there is no contact-creation route, so contacts exist only through the seed (L-21). | No |
| D-37 | **Successful `project.create`, `project.write`, `member.role.write` and `contact.private.read` write an `allow` audit row in the same transaction as the change** (D-10 applied); a failed audit write rolls the change back and answers 503. Ordinary reads write nothing. | **Yes** (policy), **approved 2026-11-19** |
| D-38 | **A write that keeps losing a race fails closed.** The write statement is retried at most 3 times; before each retry the gates are re-run and the pre-checks repeated, so a race that changed the answer is reported as what it now is (404, 403, 409, 429). If it still changes no row after 3 attempts the answer is `503 service.unavailable`, with **no** audit row of either kind. | **Yes** (policy), **approved 2026-11-19** |
| D-39 | **Audit `resource_type` of an `allow` row follows `resource_id`** (a created project is `project`), while the `deny` rows of the same route describe the route's target (`tenant` for `POST /tenants/{t}/projects`). Consistent with D-24. | No |
| D-40 | **Constant work on every not-visible path.** Gates 3-5 run the same lookups, in the same order, for every outcome, with a nil id standing in for anything that does not exist; only then are the gates decided, in their documented order. A hidden-market, foreign-tenant, revoked-member and missing target therefore execute the identical SQL sequence per route (a deterministic test enforces it). Measured before/after on this machine: hidden vs missing **+23.5% to +0.9%**, foreign vs missing **+10.7% to +0.7%**. Responses, statuses, audit rows and the order of decisions are unchanged. Not covered (they reveal nothing about resources): gate 2 (disabled principal), D-11 (malformed ids), and the 401 path. | **Yes** (design; touches approved M1 gate code), **approved 2026-11-19** |
| D-41 | **The vulnerable lab is isolated in eight layers, each tested alone** (`docs/vulnerable-lab.md` s1): no import from the default app, absent from the wheel, one-way import allow-list with no network client, start-up guard, request guard, Unix-socket launcher, container without a network, visible marking. The **container is the real network boundary**; the environment flags are guardrails that fail closed. | **Given** (isolation review approved by the owner, 2026-11-20) |
| D-42 | **Four independently switchable flaws** (tenant predicate omitted, role check missing, private property serialized, market boundary omitted) and a **differential test**: with no flaw enabled the vulnerable app answers like the patched app (status, media type and body minus the request id) to a 323-request matrix of authorization outcomes and successful responses over every fixture principal, an anonymous caller, a garbage token and valid-token header variants (wrong scheme, double space, lower-case scheme, two headers). Request-validation error DETAIL is simplified and out of scope. The vulnerable app reuses only authentication, the schema and generic middleware; it does not reuse the patched gates, handlers or service. | No |
| D-43 | **`tenantlab/lab/vulnerable/` is excluded from the built wheel.** Installing the package can never install the broken code; it exists only in a source checkout (and in the container image built from one). Consequence: another tool that needs it as a fixture takes it from a tagged source checkout. | **Given** (isolation review approved by the owner, 2026-11-20) |
| D-44 | **Data guard: refuse to start unless every principal's e-mail ends in `@tenantlab.invalid`, and the database is a SQLite file.** A broken app must not be pointed at real data or a networked database. | **Given** (isolation review approved by the owner, 2026-11-20) |
| D-45 | **Request guard independent of the launcher:** a request whose peer is not loopback, or whose local server address is a non-loopback IP literal, is refused with 403 even if the process was bound to `0.0.0.0`. A Unix-socket peer is local. | No |
| D-46 | **Docker tests are marked `docker` and FAIL, not skip, when no daemon is available**, with a message naming the deselect command (`-m "not docker"`). A missing daemon is never reported as a pass. | **Given** (isolation review approved by the owner, 2026-11-20) |
| D-47 | **Every response of the vulnerable app carries `X-Tenantlab-Vulnerable: deliberately-broken-lab`** and the process logs a banner listing the enabled flaws; it writes no audit rows. | No |
| D-48 | **A Unix socket is protected by its directory, not by its file mode.** uvicorn `chmod`s a Unix socket to 0666 after binding, which overrode the launcher's `umask` (the claim "owner-only" in the first design was false, found by a test: the socket was world-connectable). The launcher now refuses a socket directory that group or others can traverse and `chmod`s the socket to 0600 once bound. | **Given** (isolation review approved by the owner, 2026-11-20) |
| D-49 | **CI (`.github/workflows/ci.yml`) is safe by construction.** Every action is pinned to a full commit SHA (with the version in a comment); top-level `permissions: {}` and `contents: read` per job; `pull_request`, never `pull_request_target`; `persist-credentials: false`; no secrets are used; `UV_FROZEN=1` so CI never re-resolves dependencies; gitleaks is downloaded at a pinned version and **checksum-verified**; Dependabot keeps the pins and the lockfile current. Three jobs: lint+types+tests, the container tests (Docker on the runner), and `pip-audit` + a full-history secret scan. | No |
| D-50 | **The Docker tests run in CI and still fail, not skip, without a daemon (D-46).** The runner has Docker; the job runs `docker version` first so a missing daemon is a visible, separate failure. | No |
| D-51 | **Repository settings applied by the agent on the owner's instruction (2026-11-19), each read back from the API afterwards:** visibility public, private vulnerability reporting, secret scanning and push protection, Dependabot alerts and security updates, default workflow token read-only and not allowed to approve pull requests, approval required for workflow runs from **all** outside contributors, GitHub's "require actions pinned to a full SHA" setting, branch protection on `main` that requires the CI checks but does **not** apply to administrators (the owner can still push). | Given |
| D-52 | **CodeQL (python, `security-extended`) runs on push, pull request and weekly** (`.github/workflows/codeql.yml`, SHA-pinned). The vulnerable lab is **not** excluded from the scan: an unintended weakness in a guard should still be visible. First run: one alert, `py/clear-text-storage-sensitive-data` in `tools/secret_scan.py`, a **false positive** (the tool writes randomly generated fake secrets to a temp directory as a scanner canary); dismissed with that reason recorded. Dependabot is configured not to bump the pinned Python minor version (its first PR proposed 3.15 and CI rejected it). | No |
