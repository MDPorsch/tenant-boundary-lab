## WHAT RUNNING ON POSTGRESQL FOUND (four real defects, all fixed)

The spec says SQLite is not an adequate substitute for PostgreSQL row locking. It was right. Before any
new test was written, the existing M1 and M2 suites were pointed at PostgreSQL
(`TENANTLAB_TEST_DB=postgres`); then the races were written as deterministic tests. Evidence, not
opinion:

| # | Defect | How it showed | Fix |
|---|---|---|---|
| 1 | **A tenant could be left with no owner.** Two owners demoting each other at the same moment both passed "another active owner exists" against a snapshot in which the other was still active. Test result before the fix: `[200, 200]` and zero owners | `test_tl11_pg_two_owners_demoting_each_other_at_once_leave_one_owner` | the tenant row is locked `FOR UPDATE` by a role change (D-56): one demotion wins, the other is refused (403, its author is no longer an owner) |
| 2 | **The project quota could be exceeded**: two concurrent creators at 999 projects, result `[201, 201]`, 1001 rows | `test_tl20_pg_concurrent_creates_at_the_quota_never_exceed_it` | a create locks the tenant row `FOR UPDATE`: exactly one 201 and one 429 |
| 3 | **An authority change was not ordered against a write that relied on it.** Revoking a membership, downgrading a role, disabling a principal, suspending the tenant or removing a market all completed while the write was still in flight, so a write could commit after the revocation that should have stopped it | ten tests, `test_tl20_pg_an_authority_change_cannot_complete_while_...` | the write locks the principal, membership, tenant and market-access rows `FOR SHARE` before its statement, in one fixed order |
| 4 | **Every project creation failed on PostgreSQL**: an `INSERT ... SELECT` reports `rowcount == -1` through psycopg 3, which the code read as "nothing was written" and answered 503 | the first M2 test that creates a project, run on PostgreSQL | `RETURNING`; and an unknown row count now raises instead of reading as zero |

Not defects: TL-12 (eight writers on one `row_version`: exactly one 200, seven 409) already held,
because the version compare-and-set is one atomic statement.

## WHAT THE MUTATION CHECK FOUND IN MY OWN TESTS

* **One survivor: the Hypothesis properties missed a suspended tenant.** `gate4_a_suspended_tenant_is_served`
  was killed by the sweep and **survived** the properties: across 561 random requests Hypothesis never
  drew the suspended tenant's owner meeting her own tenant (it mutates earlier examples rather than
  covering a space). Fix: the properties now carry one explicit example per (caller, tenant) pair, and
  all six property mutants are killed. Hypothesis is a search, not a coverage tool.
* A first baseline run was red (one timing-sensitive test) because I used the machine while it ran; the
  rerun on a quiet machine was green. The mutation tool refuses to run on a red baseline, as designed.
* The disk of the Docker VM filled up once: each PostgreSQL container leaked a ~1 GB anonymous volume
  because I removed them without `-v`. The harness now removes the volume.
* My first TL-11 expectation was wrong (`[200, 409]`): each owner demotes the *other*, so the loser has
  just lost her authority and is refused with 403. The invariant, exactly one owner left, is unchanged.

## WHAT THIS DOES NOT SHOW

* **Reads keep the check-then-use window** (L-16): the gates and the handler run in separate
  transactions, so a read can still answer from state that changed a moment later. The spec's TL-20
  wording mentions reads; this milestone closes the write path, and says so instead of claiming more.
* Only PostgreSQL 17 was tried. The vulnerable lab and the TL-19 timing evidence stay on SQLite.
* `audit_events` is still append-only by convention (L-17): no trigger or grant was added.
* The sweep and the properties judge a response by rules written from the authorization matrix; they
  are as good as that reading of it (the matrix is the owner-approved D-24 to D-28).
