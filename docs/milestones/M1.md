## WHAT THE TESTS DID NOT SEE, AND WHAT I DID ABOUT IT

Passing on the first run proves little, so the real implementation was mutation-tested before the
supplementary tests were written (see `tools/mutation_m1.py`).

* First run, against the 96 red tests only: 42 mutants, 30 killed, **12 survived**. Two of the
  survivors were an equivalent mutant and redundant code (below). **The other ten were real gaps,
  nine distinct behaviours** (the body cap accounts for two mutants): market scope (gate 5) had no
  test at all; nor did strict path identifiers (D-11), invoice tenant coherence, the nested invoice
  route, repeated `Authorization` headers, the 413 body cap, fail-closed behaviour on a database
  error, the application's default-deny for an unknown operation, or the unknown-route 404.
* I wrote 101 supplementary end-to-end tests plus the unit suites for exactly those, then re-ran
  the mutants: all killed. The mutant table grew to 69 (token claims, audit fields, logging,
  headers, seed, settings, middleware).
* One surviving mutant was redundant code of mine (a space check that the preceding check and the
  verifier's regex already made unreachable). I deleted the code rather than write a test for it.
* One mutant (`alg_confusion`) is killed only on the verifier's internal reason: PyJWT independently
  refuses to use a PEM public key as an HMAC secret, so the forged token is rejected anyway. I say
  so rather than claim the test proves more.
* **Mistakes of mine the new tests caught:** I mapped PyJWT's subject/jti/iat errors through a
  module path that does not exist (`jwt.InvalidSubjectError`), which would have been a 500 for any
  token reaching that clause; several of my own test inputs were wrong (upper-casing an all-digit
  UUID changes nothing; a "markup" identifier containing `/` is a different path). The M0 harness
  self-check leaked SQLite connections (a ResourceWarning that appeared in unrelated tests); fixed
  with a fixture that disposes the engine.

## DECISIONS NEEDING YOUR APPROVAL

Full text in `DECISIONS.md`.

* **D-24** audit `resource_id` of a denial is the id the caller asked for (NULL if malformed; the
  parent's id for collection routes). Provisional for contacts and members.
* **D-25** an invoice is visible only if its tenant equals its project's tenant; the nested route
  needs the invoice to belong to the path project.
* **D-26** the verifier is stricter than D-03 (single `aud` string, integer times, one header, size
  caps, case-insensitive `Bearer`).
* **D-28** a denial that cannot be audited is a `503`, not the `403`.
