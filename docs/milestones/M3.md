## THE FOUR FLAWS (each a single `if` on one control; each off by default in tests)

| Flaw | OWASP | Exploit that works only with it |
|---|---|---|
| `TENANT_PREDICATE_OMITTED` | API1 | bob (viewer of A) reads tenant B's project, list and invoice; alice (owner of A, **not** a member of B) writes B's project |
| `ROLE_CHECK_MISSING` | API5 | bob PATCHes his own tenant's project and reads its private contacts |
| `PRIVATE_PROPERTY_SERIALIZED` | API3 | bob reads the private sentinel in the general project JSON |
| `MARKET_BOUNDARY_OMITTED` | API1 | alice reads the hidden-market project, its invoice and contacts; the list total counts it |

Evidence: every exploit succeeds with all flaws and fails with none; **with exactly one flaw on, only
that flaw's exploits succeed** (4 flaws x 11 exploits); the **patched app denies all 11**; and with no
flaw on, the vulnerable app answers like the patched app to a **323-request matrix** (every fixture
principal, anonymous, a garbage token, and valid-token header variants) with identical status,
media type and body.

## FINDINGS: WHAT WENT WRONG AND WHAT THE TESTS CAUGHT

* **A real defect in my own design (D-48).** I wrote that the launcher's `umask` made the Unix socket
  owner-only. A test asserting it found the socket was **mode 0666**: uvicorn `chmod`s a Unix socket
  to 0666 after binding, overriding the umask. Any local user could have connected to the vulnerable
  lab. The launcher now refuses a socket directory that group or others can traverse and `chmod`s the
  socket to 0600 once bound.
* **A wrong test design, caught before it ran.** My first "tenant predicate omitted" exploit was dave
  writing to B's project. dave is already a *viewer* in B, so the "role check missing" flaw lets him
  in too, and attribution would have been ambiguous. alice (owner of A, not a member of B) can only be
  let in by the unscoped membership lookup. The dave pair survives as its own test of the documented
  "highest role anywhere" semantics.
* **Mutation testing:** the first run killed 41 of 42. The survivor, `authentication_weakened`, removed
  the vulnerable app's `Authorization` header check; it survived because the verifier rejects most
  garbage anyway, but `Basic <valid token>` would have been accepted, a scheme confusion the patched app
  refuses. Authentication is not one of the flaws, so the parity matrix now includes valid-token header
  variants (wrong scheme, double space, lower-case, two headers).
* **Gaps I found by reasoning before the run** (not by the tool): "highest role anywhere" was untested
  (it could have become "lowest"), the socket permissions were untested, and the container control
  accepted *either* probe reaching out (a blind DNS probe would have passed). All three are now tested.
* **Coverage fell from 99% to 94%** when the package was added, which I only noticed in the fresh-clone
  gate: the launcher showed 0% and `parse_flaws` 33% because subprocess code is not measured, and several
  422/409/404 branches were untested. I added 67 in-process tests (launcher `main()` with the server
  start replaced, flaw parsing, guard and handler branches); coverage is 99% again. I also split two
  commits that had a failing intermediate state (the same grouping mistake as in M2) instead of
  disclosing it a second time.
* **My own mistakes:** a sanity check in the parity test that said `> 250` rows when the matrix had
  235; a macOS Unix-socket path limit (~104 characters) that pytest's temp directory exceeded; a
  compose error hint containing the word the secrets test watches for; a mistyped tool name; shell
  word-splitting when I tried to print the container output by hand.

## WHAT ISOLATION DOES NOT GUARANTEE (docs/vulnerable-lab.md s4, L-25..L-27)

* Only the **container** removes the network. The guards refuse non-loopback peers however the process
  was started, but a process started by hand with a network is still on the network.
* The guards were written by the author of the flaws; they are tested and mutation-tested, not
  audited by a third party.
* The container checks ran on Colima (Apple Virtualization) with Docker 29; other runtimes are untested.
* The **source distribution** still contains the vulnerable code; only the wheel excludes it (D-43).
* The lab implements six routes and writes no audit rows.

## DECISIONS FOR YOUR ISOLATION REVIEW

Full text in `DECISIONS.md`; the design is `docs/vulnerable-lab.md`.

* **D-41** eight layers, each tested alone; the container is the real network boundary.
* **D-43** the vulnerable code is excluded from the **wheel**. Consequence: `boundarycheck` will take
  it from a **tagged source checkout** as a test fixture.
* **D-44** refuse to start unless the database is a SQLite file and every principal's e-mail ends in
  `@tenantlab.invalid`.
* **D-46** the Docker tests **fail**, not skip, when no daemon is running (deselect with
  `-m "not docker"`). Is that acceptable for a plain `pytest`?
* **D-48** a Unix socket is protected by its directory; the launcher refuses an open directory.
